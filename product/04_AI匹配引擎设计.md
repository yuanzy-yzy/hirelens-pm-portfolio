# AI 匹配引擎设计

## 是否需要大模型

需要，但不应让大模型直接给出一个不可解释的“总分”。本产品采用“规则引擎 + 大模型语义判断 + 人工复核”的混合架构。

## 处理流程

### 1. 文档解析

从 JD 和简历中提取教育背景、工作年限、岗位、行业、项目、技能、地点、到岗时间等信息。

### 2. 硬条件规则

对学历、工作年限、地点、必备证书、必备技能等确定性条件进行规则校验。规则结果可复现、可解释。

### 3. 大模型语义匹配

大模型负责理解不能靠关键词直接判断的内容，例如：

- “完成嵌入式系统开发”是否能证明 C/C++ 和 Linux 工程经验；
- “对接外协团队并推动算法集成”是否能证明跨团队协作和项目推进；
- 项目经历是否真正支撑岗位要求，而不是只出现相同关键词；
- 哪些内容缺少证据，需要面试确认。

### 4. 证据化评分

每项岗位要求分别输出：

- 要求内容；
- 候选人证据；
- 匹配状态：满足、部分满足、未发现、矛盾、待核验；
- 置信度；
- 判断理由；
- 建议面试问题。

总分由各项权重计算，但必须能回溯到证据，不能只有一个黑盒分数。

### 5. 人工复核

HR 可以修改岗位权重、纠正证据、标记误判，并保留反馈记录。

## 无大模型时如何工作

无 API Key 时使用基线方案：

- 关键词归一化和同义词词典；
- 必备项布尔匹配；
- 技能、经验、项目、教育等字段加权；
- BM25/TF-IDF 或向量相似度；
- 固定模板生成缺口说明。

该方案能运行，但对隐含能力、项目上下文和跨表达语义的理解较弱。它适合作为对照组，用来证明大模型是否真正提升了匹配质量。

## 模型评估

至少建立 20 组“JD—简历”测试对，并由人工标注关键要求是否匹配。评估指标包括：

- 结构化字段准确率；
- 硬条件判断准确率；
- 证据引用正确率；
- 幻觉率；
- 人工一致率；
- 单份分析耗时；
- 单次模型调用成本。

测试数据与线上业务数据严格区分。
